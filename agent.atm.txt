Источники данных по полям
Identity & Session
Поле	Источник	Способ получения
session_id	Pi Runtime	ctx.sessionManager.getSessionId(), session_start, SessionHeader.id
developer_id	Внешняя система	Хешированный идентификатор разработчика
agent_tool	Конфигурация Pi	piConfig.name из package metadata. Значение задаётся локально и доступно в интерфейсе

session_id нужно обновлять при переключении, создании и восстановлении сессий. События Pi сами по себе не всегда содержат идентификатор сессии.

developer_id нельзя подменять идентификатором установки Pi (settings.trackingId): это разные сущности.
Task Context
Поле	Источник	Способ получения
task_id	Внешняя система	Создаётся или задаётся разработчиком
task_type	Разработчик	Выбирается вручную из заданной классификации
project	Разработчик	Выбирается вручную или связывается с проектом во внешней системе

ctx.cwd доступен, но это рабочий каталог, а не гарантированный идентификатор проекта. Его можно сохранить как техническую метаинформацию, но не использовать вместо project.
Routing
Поле	Источник	Способ получения
auth_mode	Pi Runtime	Тип авторизации: api_key, oauth, unknown
policy_id	Внешняя система	Идентификатор политики, применённой к запуску
requested_model	Pi Runtime	Физическая модель, отправленная провайдеру: message.model
resolved_model	Pi Runtime	message.responseModel ?? message.model
fallback_chain	Pi Runtime	Только реально наблюдаемые переключения моделей

Для auth_mode используются getProviderAuthStatus(provider) и isUsingOAuth(model).

Важно разделять тип авторизации и источник учётных данных. Источник можно хранить как дополнительную метаинформацию:
auth_source:
  stored
  environment
  runtime
  fallback
  models_json_key
  models_json_command
  unknown


auth_source не является дополнительным полем исходной схемы. Это вспомогательная информация сборщика. OAuth не означает автоматически подписку.

requested_model фиксирует физическую модель, отправленную провайдеру. Выбранную пользователем виртуальную модель можно сохранять отдельно как метаданные.

fallback_chain не нужно восстанавливать предположениями. Если Pi показывает переходы между моделями, фиксируем их. Если переходов нет — цепочка пустая. compat.allowedFallbackModels показывает разрешённые модели, но не фактическую цепочку.
Execution
Поле	Источник	Способ получения
request_ts	Assistant message	message.timestamp
in/out_tokens	Assistant message	message.usage.input, message.usage.output
status	Pi Runtime	stopReason, errorMessage, isError, turn_end.outcome
retry_index	Pi Runtime	auto_retry_start.attempt
stage/action_type	Pi Hooks	Нормализация событий в собственную классификацию
cost_usd	Assistant message	message.usage.cost.total

request_ts — время начала конкретного запроса, а не всего пользовательского хода. durationMs можно хранить дополнительно.

Для токенов доступны также:
cacheRead
cacheWrite
reasoning
totalTokens


message_update.usage содержит накопительные значения. Нельзя суммировать все обновления одного сообщения — нужно брать финальное значение.

status необходимо нормализовать с учётом уровня события:
- запрос модели — stopReason, errorMessage;
- выполнение инструмента — isError;
- завершение хода — turn_end.outcome;
- завершение всего запуска — agent_settled.
agent_end не является окончательной границей выполнения: после него могут происходить повторы и другие действия.

retry_index отражает доступные Pi повторы агента. Повторы HTTP-запросов на уровне провайдера могут быть невидимы.

cost_usd берётся из message.usage.cost.total. Стоимость может быть расчётной, а не подтверждённой провайдером. totalFromProvider можно сохранить как дополнительный признак происхождения стоимости.
Классификация stage/action_type
Для нормализации событий предлагается использовать фиксированный enum:
user_input
llm_request
tool_call
tool_result
tool_error
context_compaction
branch_change
model_selection
retry
agent_completion
agent_abort


Соответствие событиям Pi:
Pi Event	action_type
message_start с пользовательским сообщением	user_input
message_start с запросом модели	llm_request
tool_execution_start	tool_call
tool_execution_end	tool_result
tool_execution_end с isError=true	tool_error
События компактизации контекста	context_compaction
События переключения ветки	branch_change
model_select, model_change	model_selection
auto_retry_start	retry
agent_settled с успешным завершением	agent_completion
agent_settled с прерыванием	agent_abort

Это наша нормализация, а не встроенная классификация Pi. Её версию следует фиксировать отдельно, чтобы изменения классификации не ломали сравнение исторических данных.
Outcome
Поле	Источник	Способ получения
outcome_link	Pi + внешние системы	Ссылка на файлы, коммит, PR или другой артефакт результата
outcome_type	Внешняя система	Классификация результата задачи

outcome_link предлагается реализовать через внешнюю привязку с автоматизацией.

Первоначально можно получать список файлов из доступных данных Pi:
- details.readFiles;
- details.modifiedFiles;
- bashExecutionMessage.fullOutputPath.
Это позволит фиксировать хотя бы часть файлов, с которыми работал агент. Однако такой список не гарантирует полноту: изменения через Bash, внешние инструменты и другие процессы могут не попасть в него.

Далее можно автоматизировать привязку к Git:
- определить репозиторий и рабочую ветку;
- сопоставить выполнение с изменениями;
- получить commit hash;
- связать результат с PR;
- при необходимости привязать CI-артефакты.
Таким образом, outcome_link не ограничивается списком файлов Pi. Он может стать полноценной ссылкой на результат выполнения во внешней системе.

outcome_type должен отражать реальный результат задачи, например, выполнена ли она успешно, частично или не выполнена. Техническое завершение Pi не доказывает успешность задачи.
3. Дополнительные технические замечания
Границы выполнения. Для определения завершения запуска лучше использовать agent_settled, а не agent_end.

Дедупликация. Hooks и JSONL могут содержать сведения об одном событии. Нужно исключать повторную запись. Предпочтительно использовать messageEntryId, toolResultEntryIds; если их нет — составной ключ из session_id, роли, timestamp и toolCallId.

JSONL-сессии. Файлы сессий Pi полезны для восстановления пропущенных данных и ретроспективного анализа. В них также могут присутствовать события компактизации, ветвления и изменения контекста.

Приватность. Не собирать содержимое сообщений, системные промпты, файлы контекста и полные результаты инструментов без отдельной необходимости. Не читать секреты из auth.json.

Версии. Нужно учитывать версию Pi и формат заголовка сессии, поскольку структура JSONL может меняться.

Производительность. Hooks Pi ожидаются асинхронно, поэтому тяжёлую обработку не следует выполнять непосредственно внутри обработчиков. Лучше быстро сформировать событие и передать его в очередь сборщика.

5. Итоговые решения
1. Исходная схема из 19 полей сохраняется без изменений.
2. task_id, task_type и project задаются разработчиком или связываются с внешней системой.
3. agent_tool определяется из конфигурации Pi и учитывается в интерфейсе.
4. requested_model — физическая модель, отправленная провайдеру.
5. fallback_chain содержит только наблюдаемые переключения.
6. auth_mode описывает тип авторизации, а источник учётных данных остаётся вспомогательной метаинформацией.
7. stage/action_type использует фиксированную нормализованную классификацию.
8. outcome_link связывается с внешними результатами автоматически: сначала доступные файлы Pi, затем Git, PR и CI.
9. outcome_type определяется отдельно и не выводится только из технического статуса Pi.


АРХИТЕКТУРА СИСТЕМЫ RUNTIME TRACE

1. КОНЦЕПЦИЯ СИСТЕМЫ

Основная единица записи — один запрос к LLM (per-request record).
Единица анализа — задача (task).

Runtime Transaction — одна запись о запросе к LLM со своими Routing и Execution данными.

Task — совокупность runtime-транзакций, объединённых общим task_id. На уровне задачи анализируется работа агента и фиксируется итоговый результат.

Session — одна непрерывная сессия работы агента.

Action — отдельное действие внутри сессии: вызов инструмента, компактизация контекста, переключение модели и другие события.

Для первой версии принимается правило:
Одна сессия Pi = одна задача.

При этом на уровне базы данных сохраняется возможность связывать одну задачу с несколькими сессиями. Это позволит в будущем объединять несколько сессий в одну задачу.

Все события внутри сессии связываются с одной задачей и упорядочиваются по timestamp.

Жизненный цикл задачи контролируется через внешний интерфейс:
- создание задачи;
- привязка сессии Pi;
- сбор данных;
- завершение задачи;
- фиксация результата.

Правила определения:

error — Pi или провайдер вернул ошибку.

cancelled — запрос был прерван.
rate_limited — провайдер ограничил частоту запросов.

3. ВНЕШНИЙ КОНТЕКСТ И ИДЕНТИФИКАТОРЫ

project — внешний идентификатор проекта или название корневого проекта.

4. АРХИТЕКТУРА СБОРА ДАННЫХ

Главный принцип:

Система не управляет работой Pi и не зависит от его TUI. Она наблюдает за работой агента, собирает данные и предоставляет собственный интерфейс для управления задачами и анализа.

Основные компоненты:

1. ВНЕШНИЙ ИНТЕРФЕЙС

Создание и управление задачами.
Выбор разработчика и проекта.
Выбор типа задачи.
Привязка Pi-сессии к задаче.
Завершение задачи и фиксация результата.
Просмотр транзакций, сессий и аналитики.

2. CORE API

Управление задачами и сессиями.
Приём событий от адаптеров.
Связывание данных.
Управление жизненным циклом.
Предоставление данных интерфейсу.

Получение данных из Pi.

Обработка и нормализация событий.

Связывание событий с сессиями и задачами.

Восстановление пропущенных данных.

5. POSTGRESQL

Хранение исходных событий, runtime-транзакций, задач, сессий и артефактов.


5. ПРОЦЕСС РАБОТЫ СИСТЕМЫ

1. Пользователь создаёт задачу во внешнем интерфейсе.
2. Указывает developer_id, project и task_type.
3. Привязывает Pi-сессию к задаче.
4. Pi Adapter начинает собирать события Hooks.
5. Полученные события сохраняются локально.
6. Event Processing нормализует события и формирует per-request записи.
7. JSONL используется для сверки и восстановления пропущенных данных.
8. Все данные связываются с task_id и session_id.
9. Пользователь завершает задачу через интерфейс.
10. Пользователь указывает outcome_type.
11. Система связывает задачу с доступными артефактами.


6. НАДЁЖНОСТЬ И ОБРАБОТКА СОБЫТИЙ

На первом этапе не использовать RabbitMQ, Kafka или Redis.

PostgreSQL будет одновременно постоянным хранилищем событий и очередью обработки.

Механизм работы:

1. Pi Adapter получает событие.
2. Событие сразу сохраняется в таблицу raw_events.
3. Каждое событие получает уникальный ключ для дедупликации.
4. Обработчик выбирает необработанные события.
5. Событие нормализуется и связывается с runtime-транзакцией.
6. После успешной обработки событие помечается обработанным.
7. При ошибке событие остаётся в базе и может быть обработано повторно.

Используется подход DB-backed Queue / Transactional Outbox.

Система не должна терять уже полученные события при перезапуске приложения.

JSONL используется для дополнительной сверки и восстановления пропущенных событий.

Все операции обработки должны быть идемпотентными.


7. ХРАНЕНИЕ ДАННЫХ

Основная база данных — PostgreSQL.

Предлагаемые таблицы:

developers — разработчики.

projects — проекты.

tasks — задачи и их жизненный цикл.

sessions — сессии Pi.

raw_events — исходные события Pi.

runtime_transactions — записи на каждый LLM-запрос.

artifacts — файлы, коммиты, PR и другие результаты.

task_artifacts — связи задач с артефактами.

integration_sources — подключённые источники данных.

Для raw_events исходный JSON сохраняется в JSONB.

Для runtime_transactions используются типизированные столбцы согласно исходной схеме авторов.

Преимущества такого подхода:

- возможность повторно обрабатывать исходные события;
- сохранение информации, которая пока не входит в 19 полей схемы;
- возможность менять нормализатор без потери исходных данных;
- аналитика через SQL;
- восстановление истории выполнения.


8. ПЕРЕДАЧА ДАННЫХ

Взаимодействие компонентов осуществляется через локальный HTTP API.

Предварительные endpoints:

POST /api/v1/events
POST /api/v1/sessions
POST /api/v1/tasks

Внешний интерфейс использует Core API для создания задач, управления ими и просмотра результатов.


9. ВЕРСИОНИРОВАНИЕ

Необходимо отдельно учитывать:

taxonomy_version — версия классификаторов и правил нормализации.

Это технические метаданные, а не дополнительные поля исходной схемы.

Версионирование позволит сохранять совместимость данных при изменении форматов событий, классификаторов и адаптеров.


10. ПРИВАТНОСТЬ

Система работает по принципу local-first.

Можно сохранять транскрипты, контекст, результаты инструментов и другие данные, необходимые для последующего анализа.

Запрещено сохранять секреты:

- API-ключи;
- OAuth-токены;
- приватные ключи;
- пароли;
- секреты из конфигурационных файлов.

Слой обнаружения и редактирования секретов должен работать до сохранения данных.

Секреты могут находиться не только в auth.json, но и в переменных окружения, сообщениях, выводе инструментов и логах.


11. РАБОТА С АРТЕФАКТАМИ (OUTCOME_LINK)

outcome_link задаётся через внешнюю систему.

Внешняя система отвечает за привязку результата выполнения задачи:
- ссылка на изменённые файлы;
- ссылка на Git commit;
- ссылка на Pull Request;
- ссылка на CI-артефакты;
- другие ссылки на результаты работы.

Привязка может выполняться пользователем через интерфейс или автоматически внешними интеграциями, например Git и CI.

Pi Adapter не отвечает за формирование outcome_link. Его задача — собирать данные о работе агента.

outcome_type также задаётся через внешний интерфейс при завершении задачи.

Таким образом, оба поля Outcome контролируются внешней системой:
- outcome_link — где находится результат;
- outcome_type — каким оказался результат.


12. ОТКРЫТЫЕ ВОПРОСЫ И ПРЕДЛОЖЕННЫЕ РЕШЕНИЯ

Обнаружение Pi-сессий:

Пользователь выбирает сессию в интерфейсе. Система автоматически обнаруживает доступные сессии Pi.

Восстановление пропущенных событий:

Сверка Hooks и JSONL по идентификаторам записей. При отсутствии идентификаторов — использование составных ключей.

Незавершённая задача:

Предлагаемые статусы задачи:

in_progress
completed
abandoned

Обработка артефактов:

На первом этапе — список файлов Pi. Далее — автоматическая Git-интеграция.

Согласованность данных:

Идемпотентная обработка событий и дедупликация.

Запуск сборщика:

Локальный процесс, независимый от TUI Pi.

Несколько экземпляров Pi:

Для каждого процесса и сессии должен существовать отдельный контекст адаптера. События разных сессий не должны смешиваться.


ГЛАВНЫЙ ПРИНЦИП:

Система должна быть независимым от конкретного TUI слоем наблюдения за AI coding agents. Адаптеры собирают данные из разных агентов, ядро нормализует и связывает их, а внешний интерфейс позволяет управлять задачами, анализировать работу и изучать результаты.


# **USER FLOW И ВНУТРЕННИЕ ПРОЦЕССЫ RUNTIME TRACE**

## **1. Общий принцип работы**

Пользователь работает с задачами через интерфейс Runtime Trace, а не через интерфейс Pi.

Runtime Trace отвечает за:

- создание и управление задачами;
- привязку сессий Pi;
- сбор и хранение данных;
- анализ запросов к LLM;
- фиксацию результатов;
- просмотр истории и статистики.

Pi остаётся средой, в которой AI-агент выполняет работу. Пользователь может взаимодействовать с ним через TUI или CLI. Runtime Trace не зависит от того, какой интерфейс Pi используется.

Основная связь данных:

```
Developer
    |
    v
  Project
    |
    v
   Task
    |
    v
  Session
    |
    v
Runtime Transactions
    |
    v
   Actions
```

Одна задача в первой версии связана с одной сессией Pi. Внутри сессии собираются все события и LLM-запросы. Каждая runtime-транзакция привязывается к `task_id` и `session_id`.

Единица записи — один LLM-запрос.\
Единица анализа — задача.

## **2. Пользовательский сценарий (User Flow)**

### **Этап 1. Создание задачи**

Пользователь открывает Runtime Trace и нажимает Create Task.

Заполняет:

- Название задачи.
- Описание задачи.
- Developer.
- Project.
- Task Type.
- При необходимости Policy ID.

Пример:

```
Task: Implement user authentication

Developer: @gosha
Project: my-backend
Task Type: feature_development
Policy ID: default-policy
```

После создания система:

- генерирует `task_id`;
- сохраняет задачу в PostgreSQL;
- устанавливает статус `pending`;
- сохраняет контекст задачи.

### **Этап 2. Привязка сессии Pi**

Пользователь переходит к привязке сессии.

Интерфейс показывает обнаруженные сессии Pi:

- идентификатор сессии;
- время создания;
- рабочую директорию;
- версию Pi;
- статус сессии;
- другую доступную информацию.

Пользователь выбирает нужную сессию.

После привязки система:

- получает `session_id`;
- связывает его с `task_id`;
- проверяет, не привязана ли сессия к другой активной задаче;
- сохраняет связь в PostgreSQL;
- переводит задачу в `in_progress`.

В первой версии действует ограничение: одна активная задача — одна сессия.

Если подходящей сессии ещё нет, пользователь сначала создаёт её в Pi, после чего выбирает в Runtime Trace.

### **Этап 3. Работа над задачей**

Пользователь работает с агентом в Pi привычным способом.

Никаких дополнительных действий в Runtime Trace во время работы выполнять не нужно.

Система автоматически собирает данные.

В интерфейсе можно видеть:

```
Task: Implement user authentication
Status: In Progress

Session: pi-session-123

LLM Requests: 14
Tool Calls: 32
Input Tokens: 48 200
Output Tokens: 12 400
Estimated Cost: $0.42

Last Activity: 20:45:12
```

Также доступна хронология действий:

- запросы к LLM;
- ответы LLM;
- вызовы инструментов;
- ошибки;
- переключения моделей;
- повторы;
- компактизация контекста.

### **Этап 4. Завершение задачи**

Когда пользователь закончил работу, он возвращается в Runtime Trace и нажимает Complete Task.

Открывается форма завершения:

```
Outcome Type:
  success
  partial_success
  failure
  abandoned
  unknown

Outcome Link:
  URL или ссылка на результат работы
```

`outcome_link` задаётся через внешний интерфейс. Пользователь может вставить ссылку самостоятельно либо использовать автоматическую привязку через Git, CI и другие интеграции.

После подтверждения система:

- выполняет финальную сверку событий с JSONL;
- обрабатывает оставшиеся события;
- проверяет наличие незавершённых транзакций;
- сохраняет `outcome_type`;
- сохраняет `outcome_link`;
- фиксирует время завершения;
- переводит задачу в `completed` или `abandoned` в зависимости от выбранного результата.

Если пользователь закрыл задачу с `failure` или `partial_success`, её статус всё равно может быть `completed`: технически работа над задачей завершена, но результат оказался неуспешным или частичным. Статус задачи и `outcome_type` — разные характеристики.

### **Этап 5. Анализ задачи**

После завершения пользователь открывает страницу задачи.

Там отображаются:

1. Общая информация о задаче.
2. Developer и Project.
3. Привязанная сессия.
4. Все LLM-запросы.
5. Использованные модели.
6. Токены и стоимость.
7. Ошибки и повторы.
8. Последовательность действий агента.
9. Outcome Link.
10. Outcome Type.

Пользователь может открыть отдельную runtime-транзакцию и изучить её детали.

## **3. Что происходит под капотом**

### **3.1. Обнаружение сессий Pi**

Runtime Trace должен обнаруживать доступные сессии Pi без необходимости открывать их через TUI.

Для этого используются:

- каталоги сессий Pi;
- заголовки JSONL-файлов;
- SDK/RPC, если нужны дополнительные сведения о текущем состоянии;
- информация о версии Pi.

Система формирует список доступных сессий и показывает его пользователю.

После выбора сессии сохраняется связь:

```
task_id -> session_id
```

### **3.2. Подключение Pi Adapter**

Pi Adapter работает как расширение или интеграционный компонент Pi.

Он подписывается на необходимые Hooks и получает события во время работы агента.

Например:

```
message_start
message_update
message_end

tool_execution_start
tool_execution_update
tool_execution_end

turn_start
turn_end

auto_retry_start
auto_retry_end

model_select
model_change

agent_settled
```

При получении события Adapter:

1. Определяет текущую сессию.
2. Получает связанный `task_id`.
3. Добавляет технические метаданные события.
4. Передаёт данные локальному Core API.

Сам Adapter не должен выполнять тяжёлую обработку. Его главная задача — надёжно получить событие и передать его дальше.

### **3.3. Приём и сохранение событий**

Core API получает события от Pi Adapter.

До нормализации исходное событие сохраняется в `raw_events`.

Пример внутреннего представления:

```
{
  "event_id": "event-123",
  "source": "pi_hook",
  "session_id": "session-123",
  "task_id": "task-456",
  "event_type": "message_end",
  "timestamp": "2026-11-21T20:45:12Z",
  "payload": {}
}
```

Это пример технического формата события, а не новая схема runtime-транзакции.

Затем событие передаётся в обработку.

### **3.4. Нормализация событий**

Event Processing преобразует события Pi в единый внутренний формат.

Например:

```
Pi Event:
tool_execution_start

Normalized Action:
tool_call
```

```
Pi Event:
auto_retry_start

Normalized Action:
retry
```

```
Pi Event:
agent_settled

Normalized Action:
agent_completion
```

Для каждого типа события определяются правила извлечения данных.

На этом этапе также:

- сопоставляются события одного запроса;
- определяется модель;
- извлекаются токены и стоимость;
- определяется статус;
- формируются связи между запросами и действиями;
- вычисляются дополнительные агрегаты.

### **3.5. Формирование Runtime Transaction**

Главная задача обработчика — собирать отдельные LLM-запросы из последовательности событий Pi.

Например:

```
message_start
    |
    v
message_update
    |
    v
tool_execution_start
    |
    v
tool_execution_end
    |
    v
message_start
    |
    v
message_end
```

Обработчик сопоставляет события и формирует записи runtime-транзакций.

Одна запись соответствует одному запросу к LLM.

```
Runtime Transaction #1
  session_id
  task_id
  requested_model
  resolved_model
  request_ts
  in_tokens
  out_tokens
  status
  cost_usd
  ...
```

Вызовы инструментов и другие действия не становятся отдельными LLM-транзакциями. Они сохраняются как события и действия, связанные с соответствующим контекстом выполнения.

Для связывания используются доступные идентификаторы Pi: `messageEntryId`, `toolCallId`, `toolResultEntryIds` и другие. Если идентификаторов недостаточно, применяется дополнительная логика сопоставления.

### **3.6. Сверка с JSONL**

Hooks используются для сбора данных в реальном времени.

JSONL используется как дополнительный источник истории.

Периодически или при завершении задачи система:

1. Читает соответствующий файл сессии.
2. Проверяет, какие записи уже получены через Hooks.
3. Находит пропущенные события.
4. Добавляет недостающие данные.
5. Обновляет нормализованные записи.
6. Проверяет целостность последовательности.

Важно: одно событие не должно попасть в базу дважды.

Для этого используется дедупликация по идентификаторам событий, записей Pi и составным ключам.

### **3.7. Работа с конфигурацией Pi**

Система анализирует конфигурационные данные Pi, необходимые для понимания маршрутизации.

Из них можно получать:

- доступные модели;
- виртуальные модели;
- разрешённые fallback-модели;
- настройки маршрутизации;
- данные об источнике авторизации.

Фактическая модель запроса определяется по событиям выполнения, а не только по конфигурации.

Секреты и учётные данные не сохраняются.

### **3.8. Работа с внешней системой**

Внешняя система отвечает за данные, которые Pi не может достоверно предоставить:

- developer_id;
- project;
- task_id;
- task_type;
- policy_id;
- outcome_link;
- outcome_type.

Она также управляет жизненным циклом задачи.

Интеграции Git и CI могут автоматически связывать задачу с коммитами, PR и результатами тестирования.

Pi Adapter за эти операции не отвечает.

## **4. Хранение и обработка**

В PostgreSQL разделяются три основных уровня данных.

**Первый уровень — Raw Events.**

Исходные события, полученные от Pi и других источников. Они сохраняются для аудита, восстановления и повторной обработки.

**Второй уровень — Runtime Transactions.**

Нормализованные записи по каждому LLM-запросу согласно 19 полям исходной схемы.

**Третий уровень — Task Data.**

Задачи, сессии, разработчики, проекты и результаты.

`outcome_link` и `outcome_type` относятся к уровню задачи. Их не нужно дублировать в каждой записи LLM-запроса. При формировании отчёта по исходной схеме данные задачи связываются с её runtime-транзакциями.

### **Очередь обработки**

На первом этапе используется PostgreSQL как постоянное хранилище событий и очередь обработки.

Последовательность:

```
Pi Adapter
    |
    v
Core API
    |
    v
PostgreSQL: raw_events
    |
    v
Event Processor
    |
    v
Normalization
    |
    v
Runtime Transactions
```

Если обработчик аварийно завершился, необработанные события остаются в базе и могут быть обработаны повторно.

Если Core API или PostgreSQL временно недоступны, Pi Adapter должен сохранять события в локальный постоянный буфер и отправлять их после восстановления соединения. Это необходимо, чтобы не зависеть от доступности основного приложения в момент выполнения агента.

## **5. Поведение при нестандартных ситуациях**

**Pi завершился аварийно.**

Система сохраняет уже полученные данные. После обнаружения завершения процесса проверяет JSONL и восстанавливает пропущенные записи. Задача остаётся незавершённой до решения пользователя.

**Runtime Trace перезапустился.**

Система восстанавливает состояние задач и сессий из PostgreSQL. Очередь продолжает обработку необработанных событий.

**Сеть или Core API временно недоступны.**

Adapter использует локальный буфер и повторяет передачу событий.

**Пользователь закрыл задачу, но остались необработанные события.**

Система выполняет финальную сверку JSONL и обработку накопленных данных. Если завершить обработку не удалось, задача не должна молча терять события: интерфейс должен показать проблему и позволить повторить синхронизацию.

**Пользователь продолжает работу после завершения задачи.**

Система не должна автоматически добавлять новые события в закрытую задачу. Для продолжения создаётся новая задача или выполняется явное повторное открытие сессии и задачи с сохранением истории.

**Одна сессия уже привязана к другой активной задаче.**

Интерфейс запрещает вторую привязку, пока пользователь явно не изменит существующую связь.

## **6. Что в итоге получает пользователь**

Runtime Trace должен скрывать всю сложность сбора и обработки данных.

Пользователь выполняет только несколько действий:

1. Создаёт задачу.
2. Выбирает сессию Pi.
3. Работает с агентом как обычно.
4. Завершает задачу и указывает результат.
5. Изучает собранные данные.

Всё остальное — обнаружение событий, сбор Hooks, чтение JSONL, восстановление, дедупликация, нормализация, связывание запросов, расчёт токенов и стоимости, хранение и аналитика — выполняется автоматически.

**Главный принцип продукта: пользователь управляет контекстом и результатом работы, система автоматически собирает и организует всё, что можно получить программно.**
