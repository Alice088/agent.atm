# DESIGN.md — Runtime Trace

## 1. Product Design

**Runtime Trace — Task Control Center for AI Coding Agents.**

Интерфейс предназначен для управления задачами, привязки сессий AI-агентов, отслеживания выполнения и анализа результатов.

Это не IDE, не терминал и не универсальный observability dashboard.

Основная задача интерфейса — дать разработчику возможность в любой момент ответить на вопросы:

- Какие задачи сейчас выполняются?
- Что происходит с каждой задачей?
- Какой агент и какая сессия с ней связаны?
- Когда была последняя активность?
- Есть ли ошибки или проблемы со сбором данных?
- Сколько запросов, токенов и денег потрачено?
- Чем закончилась задача?

**Основной принцип UX: Task-first.**

Разработчик управляет задачами, а система самостоятельно собирает и организует технические данные.

## 2. UX Principles

### 2.1. Task-centric

Задача — главный объект интерфейса.

Основные действия должны быть доступны непосредственно из списка задач и страницы конкретной задачи.

Не заставлять пользователя постоянно переходить между отдельными разделами Sessions, Events, Transactions и Dashboard.

### 2.2. Fast Navigation

Пользователь должен быстро переключаться между задачами.

Предусмотреть:
- быстрый поиск задач;
- список последних открытых задач;
- переключатель текущей задачи;
- горячие клавиши;
- прямой переход к задаче из таблиц и событий.

### 2.3. State Visibility

Состояние задачи, агента и сбора данных всегда должно быть понятным.

Не объединять их в один статус.

Например, задача может быть активной, агент — простаивать, а данные — полностью синхронизированы.

### 2.4. Minimal Interaction

Основной сценарий должен требовать минимум действий:

1. Создать задачу.
2. Привязать сессию Pi.
3. Работать с агентом.
4. Отслеживать выполнение.
5. Завершить задачу и зафиксировать результат.

Всё остальное выполняется автоматически.

### 2.5. Progressive Disclosure

Показывать сначала важную информацию.

Технические подробности, JSON, исходные события и расширенные параметры доступны по запросу.

Не показывать все 19 полей runtime-схемы на главном экране.

### 2.6. Clarity over Decoration

Каждый элемент интерфейса должен выполнять конкретную функцию.

Не добавлять декоративные графики, лишние карточки, сложные визуализации и информационные блоки без практической необходимости.

## 3. Visual Direction

**Visual Concept: Minimal Engineering Console / Blueprint Interface**

Интерфейс должен напоминать современный инженерный инструмент.

Визуальные характеристики:
- моноширинная типографика;
- тонкая координатная сетка;
- острые углы;
- тонкие границы;
- прямоугольные панели;
- компактные таблицы;
- строгая геометрия;
- минимум декоративных элементов.

Визуальная сложность должна быть низкой, информационная плотность — высокой.

### 3.1. Typography

Основной шрифт: IBM Plex Mono.

Альтернативы:
- JetBrains Mono;
- Geist Mono.

Использовать моноширинную типографику для навигации, заголовков, таблиц, метаданных, идентификаторов и основных элементов управления.

Размеры:
- Page Title: 20–22px.
- Section Title: 14–16px.
- Body: 13–14px.
- Table: 12–13px.
- Metadata: 11–12px.

Не использовать слишком маленький текст ради увеличения плотности.

Иерархию создавать через размер, насыщенность и контраст.

### 3.2. Color Palette

Основная тема — Dark Blueprint.

Background:
- Main: #0C111B
- Surface: #111A27
- Elevated: #172233

Borders:
- Primary: #29384B
- Secondary: #1E2A3A

Text:
- Primary: #E1E8F0
- Secondary: #9AAABD
- Muted: #65778D

Accent:
- Blue: #6EA8FE
- Cyan: #67D5E8

Status:
- Success: #42C88A
- Warning: #E7B45A
- Error: #EA6B75
- Neutral: #8291A5

Цвета статусов использовать последовательно во всём приложении.

Не использовать несколько акцентных цветов одновременно.

### 3.3. Blueprint Grid

Сетка — одна из основных частей визуальной идентичности.

Использовать:
- тонкую квадратную сетку;
- шаг около 24–32px;
- чуть более выраженные основные линии;
- низкий контраст;
- геометрически выровненные панели.

Сетка должна ощущаться как техническая разметка рабочего пространства.

Важно:
- не накладывать контрастную сетку на текст;
- не ухудшать читаемость таблиц;
- не добавлять сетку внутрь каждого компонента;
- использовать её преимущественно на основном фоне.

### 3.4. Geometry

Предпочтительная форма элементов:
- прямоугольники;
- острые углы;
- радиус 0–2px;
- границы толщиной 1px;
- минимальные тени.

Избегать:
- больших скруглённых карточек;
- pill-кнопок;
- стеклянных поверхностей;
- объёмных теней;
- чрезмерных градиентов.

### 3.5. General Appearance

Интерфейс не должен выглядеть как старый терминал или сложная промышленная SCADA.

Он должен быть современным, чистым и понятным.

Моноширинный шрифт и сетка задают характер. Простая композиция и достаточные отступы сохраняют удобство.

## 6. Task Lifecycle and States

Необходимо разделять жизненный цикл задачи, состояние агента и состояние сбора данных.

Это три независимых характеристики.

### 6.1. Task State

Статус задачи контролируется внешним интерфейсом.

```text
pending
in_progress
awaiting_outcome
completed
abandoned
```

Значения:

PENDING — задача создана, сессия ещё не привязана.

IN_PROGRESS — задача выполняется или ждёт продолжения работы. В макетах отображается как ACTIVE.

AWAITING_OUTCOME — задача закрыта человеком, окно ожидания артефакта открыто; линковка идёт
своим темпом, вердикт уже записан, но класс артефакта не окончателен.

COMPLETED — артефакт привязан либо задача не предполагает артефакта.

ABANDONED — окно ожидания истекло без артефакта. Отказ человека — это вердикт
(`human_verdict = abandoned`), а не статус: он не доказывает отсутствие артефакта.

Нормативный перечень и переходы — `SPEC.md` §11. Сверка при завершении не является состоянием
задачи: это состояние сбора (`catching_up`), поэтому отдельного статуса `finalizing` нет.

### 6.2. Agent State

Состояние Pi определяется по доступным runtime-событиям и информации о сессии.

```text
running
idle
ended
unavailable
unknown
```

RUNNING — наблюдается выполнение агента.

IDLE — новых событий некоторое время нет, но сессия не считается завершённой.

ENDED — получено подтверждение завершения сессии или запуска.

UNAVAILABLE — источник данных или процесс наблюдения недоступен.

UNKNOWN — достоверно определить состояние невозможно.

Не считать отсутствие событий доказательством того, что агент завершил работу.

### 6.3. Collection State

Состояние сбора и синхронизации:

```text
live
catching_up
up_to_date
delayed
error
```

LIVE — события поступают в реальном времени.

CATCHING_UP — выполняется восстановление истории.

UP_TO_DATE — известные события синхронизированы.

DELAYED — данные поступают с задержкой.

ERROR — возникла ошибка сбора или обработки.

### 6.4. State Presentation

В интерфейсе эти характеристики всегда отображаются отдельно.

Пример:

```text
TASK       ACTIVE
AGENT      IDLE
COLLECTION UP TO DATE
```

Так пользователь не путает состояние задачи с состоянием агента или сборщика.

## 7. Create Task Flow

Создание задачи должно быть простым.

По нажатию New Task открывается компактная форма.

### Step 1 — Task Context

Поля:
- Task Name;
- Description;
- Project;
- Developer;
- Task Type;
- Policy ID (optional).

Основная кнопка:

CREATE TASK

После создания система:
- генерирует task_id;
- сохраняет контекст;
- создаёт задачу со статусом pending;
- открывает экран привязки сессии.

### Step 2 — Attach Session

Показывается список обнаруженных сессий Pi.

```text
AVAILABLE PI SESSIONS

SESSION ID        WORKING DIRECTORY    PI VERSION    LAST ACTIVITY    STATE

session-a1        ~/projects/backend   1.6.0         Just now         ACTIVE
session-b2        ~/projects/payments  1.6.0         5 min ago        IDLE
session-c3        ~/projects/frontend  1.6.0         Yesterday       ENDED
```

Показывать только основные сведения. Полный session_id доступен по наведению или в деталях.

Пользователь выбирает сессию и нажимает:

ATTACH SESSION

После привязки:
- создаётся связь task_id → session_id;
- проверяется отсутствие конфликтующей активной привязки;
- запускается сбор данных или выполняется подключение к уже работающему сборщику;
- задача переходит в ACTIVE.

Если сессии ещё нет, пользователь может пропустить этот шаг и привязать её позже.

## 8. Task Workspace

Это главный экран после открытия конкретной задачи.

Его задача — дать пользователю полный контроль над контекстом и состоянием задачи, не перегружая его техническими данными.

### 8.1. Task Header

```text
TASKS / IMPLEMENT AUTHENTICATION

Implement user authentication

TASK-0241
PROJECT: BACKEND
DEVELOPER: @GOSHA

[ACTIVE] [AGENT: RUNNING] [COLLECTION: LIVE]

                            [COMPLETE TASK] [...]
```

Основные действия:
- Complete Task;
- Attach/Change Session (если допустимо);
- Reopen Task;
- More.

Не добавлять элементы управления, которые система фактически не поддерживает.

Runtime Trace управляет задачей и сбором данных, но не должен изображать управление самим агентом, если соответствующая возможность Pi не реализована через SDK/RPC.

### 8.2. Metrics Strip

Под заголовком размещается одна компактная линия показателей.

```text
LLM REQUESTS     TOOL CALLS      INPUT TOKENS     OUTPUT TOKENS     COST

24               58              48.2K            12.4K             $0.42
```

При клике на показатель можно перейти к соответствующему фильтру в Transactions.

### 8.3. Workspace Navigation

Внутри задачи использовать четыре вкладки:

```text
[ACTIVITY] [REQUESTS] [CONTEXT] [RESULT]
```

Не создавать отдельные экраны для каждого типа технических данных.

### ACTIVITY

Основная рабочая вкладка и вид по умолчанию.

Показывает хронологию происходящего внутри сессии.

Пример:

```text
20:41:02  USER INPUT
           Implement user authentication

20:41:04  LLM REQUEST
           claude-sonnet
           1.2K input / 480 output

20:41:08  TOOL CALL
           read_file
           internal/auth.go

20:41:09  TOOL RESULT
           SUCCESS

20:41:12  LLM REQUEST
           claude-sonnet

20:41:18  TOOL CALL
           edit_file
           internal/auth.go
```

Элементы Activity:
- timestamp;
- action_type;
- краткое описание;
- модель, если применимо;
- статус;
- длительность, если доступна.

Фильтры:

```text
[ALL] [LLM] [TOOLS] [SYSTEM] [ERRORS]
```

Каждое событие можно раскрыть для просмотра деталей.

События одного LLM-запроса и связанные с ним действия желательно визуально группировать, если связь достоверно установлена.

Не создавать сложную графовую визуализацию. На первом этапе достаточно понятной последовательной ленты.

### REQUESTS

Таблица отдельных LLM-запросов.

```text
TIME       MODEL             STATUS     INPUT    OUTPUT   DURATION   COST

20:41:04   claude-sonnet     SUCCESS    1.2K     480      4.2s       $0.03
20:41:12   claude-sonnet     SUCCESS    2.1K     710      5.1s       $0.04
20:42:01   gpt-5             ERROR      —        —        —          —
```

Фильтры:
- Model;
- Status;
- Date;
- Search.

При выборе запроса открывается Transaction Inspector.

### CONTEXT

Информация о задаче и привязанной сессии.

TASK:
- task_id;
- task_type;
- description;
- developer_id;
- project;
- policy_id;
- created_at.

SESSION:
- session_id;
- Pi version;
- working directory;
- started_at;
- last_activity;
- session state;
- synchronization state.

Также здесь можно показать путь к исходному JSONL-файлу и технические сведения о сборщике.

### RESULT

Завершение задачи и её результат.

Показывает:
- Outcome Verdict;
- Artifact Class и список артефактов;
- время завершения.

Артефактов может быть несколько и разных типов: коммиты, PR, прогоны CI, наборы файлов. Список
пополняется по мере поступления и в любой момент после закрытия задачи: каждый элемент показывает
тип, ссылку, состояние (`подтверждён`, `кандидат`, `заменён`) и как он был найден. Элемент
«заменён» остаётся видимым со ссылкой на заменивший его артефакт — история привязки не скрывается.

В строке задачи показывается один основной артефакт и счётчик остальных: полный список доступен
на странице задачи, чтобы таблица не разрасталась.

Пользователь может изменить результат, пока задача не зафиксирована окончательно или если она была повторно открыта.

## 9. Task Completion Flow

Завершение задачи — отдельный контролируемый процесс.

При нажатии Complete Task система не должна сразу закрывать задачу.

Последовательность:

1. Перевести задачу в AWAITING_OUTCOME, состояние сбора — в CATCHING_UP.
2. Прекратить приём новых событий в контекст задачи после выбранной границы завершения.
3. Выполнить финальную сверку JSONL.
4. Обработать накопленные события.
5. Проверить незавершённые runtime-транзакции.
6. Рассчитать итоговую статистику.
7. Показать форму результата.

Форма:

```text
COMPLETE TASK

OUTCOME VERDICT

[ SUCCESS          ]
[ PARTIAL SUCCESS  ]
[ FAILURE          ]
[ ABANDONED        ]

ARTIFACT LINK

[ Enter URL or select artifact                  ]

FINAL SUMMARY

LLM Requests: 24
Tool Calls: 58
Total Tokens: 60.6K
Total Cost: $0.42

[CONFIRM COMPLETION]
```

Artifact Link необязателен: артефакт может появиться позже окна закрытия и будет привязан
автоматически. Отсутствие ссылки не блокирует завершение.

При проблемах синхронизации система должна показать предупреждение.

Нельзя молча закрывать задачу, если данные остались необработанными.

После подтверждения:
- фиксируется human_verdict;
- открывается окно линковки артефактов;
- фиксируется время завершения;
- задача переходит в COMPLETED или ABANDONED.

## 10. Transaction Inspector

Подробный просмотр одного LLM-запроса.

Он должен открываться в правой панели поверх текущего рабочего пространства либо на отдельном маршруте.

Основная задача — быстро изучить запрос и вернуться к задаче без потери контекста.

HEADER:
- transaction_id;
- timestamp;
- requested_model;
- resolved_model;
- status.

CONTENT:

IDENTITY
- session_id;
- developer_id;
- agent_tool.

TASK CONTEXT
- task_id;
- task_type;
- project.

ROUTING
- auth_mode;
- policy_id;
- requested_model;
- resolved_model;
- fallback_chain.

EXECUTION
- request_ts;
- input_tokens;
- output_tokens;
- status;
- retry_index;
- stage/action_type;
- cost_usd.

ADDITIONAL DATA
- duration;
- cache tokens;
- reasoning tokens;
- raw events;
- source references.

Использовать компактные секции с возможностью раскрытия.

Raw JSON доступен через отдельную вкладку или раскрываемый блок.

Не показывать весь JSON по умолчанию.

## 11. Quick Switcher

Быстрое переключение между задачами — важная функция продукта.

Вызывается:
- через верхнюю панель;
- горячей клавишей Ctrl+K / Cmd+K.

Пример:

```text
SWITCH TASK

[ Search tasks...                         ]

ACTIVE
> Implement authentication
  Fix payment bug
  Refactor database layer

RECENT
  Update dependencies
  Add caching
```

Поиск должен работать по:
- названию задачи;
- task_id;
- проекту;
- разработчику.

При выборе задачи открывается её Task Workspace.

Переключение не должно менять состояние самой задачи или прерывать сбор данных.

Запоминать последнюю открытую вкладку и фильтры каждой задачи.

Этот раздел предназначен для углублённого анализа, а не для ежедневного управления задачами.

Системное состояние не должно занимать много места.


При ошибке пользователь может открыть подробности.

Не выводить технические логи на главный экран.

## 14. Interaction Rules

1. Один клик по задаче открывает её рабочее пространство.
2. Переключение задач не прерывает сбор.
3. Возврат из Transaction Inspector сохраняет исходный контекст.
4. Завершение задачи всегда проходит через финальную сверку.
5. У каждого состояния есть текстовое обозначение.
6. Ошибки сопровождаются объяснением и доступным действием.
7. Опасные операции требуют подтверждения.
8. Система не должна показывать действие, которое технически невозможно выполнить.
9. Фильтры и поиск не должны сбрасываться при переходах между связанными экранами.
10. Все длительные операции показывают текущий статус.

Горячие клавиши:

Ctrl/Cmd + K — Quick Switcher.

Ctrl/Cmd + N — New Task.

Escape — закрыть панель или диалог.

Enter — подтвердить выбранное действие в поиске.

## 15. MVP Scope

Первая версия должна сосредоточиться на управлении задачами.

Обязательные экраны:

1. Tasks.
2. Create Task.
3. Session Discovery.
4. Task Workspace.
5. Activity.
6. Requests.
7. Transaction Inspector.
8. Context.
9. Result.
10. Quick Switcher.
11. Sessions.
12. Sources.
13. Settings.

Не включать в первую версию:
- сложные графы выполнения;
- расширенную аналитику;
- большие dashboard с десятками графиков;
- multi-agent orchestration UI;
- управление агентами из интерфейса;
- сложный workflow designer;
- полноценную систему оценки качества моделей.

Сначала необходимо сделать отличный интерфейс для управления задачами и просмотра их выполнения.

## 16. Final Design Direction

Runtime Trace should feel like a modern engineering workspace.

**Visual identity:**
- Dark Blueprint;
- Monospace typography;
- Subtle grid;
- Sharp corners;
- Thin borders;
- Compact tables;
- Clear status indicators.

**UX identity:**
- Task-first;
- Fast switching;
- Continuous monitoring;
- Simple lifecycle management;
- Detailed inspection when needed.

Главный экран — список задач.

Главная рабочая область — Task Workspace.

Главная визуализация — Activity Timeline.

Главный инструмент анализа — Transaction Inspector.

Интерфейс должен быть простым снаружи, но предоставлять техническую глубину по запросу.

**Runtime Trace — не место, где разработчик изучает устройство системы. Это место, где он контролирует работу AI-агентов и видит результат.**
